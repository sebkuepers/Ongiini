# Owela — contributor guide

You are working inside `owela/`, the chat-agent framework that powers
Ongiini. This file is the source of truth for how to extend the
framework without breaking the design.

Before changing code in this directory, read this whole file. Most of
it is short; the parts that matter are short on purpose.

---

## What Owela is, in 5 lines

Owela is a Python framework that runs one turn of a chat agent as a
typed sequence of steps. It's built for **small open-source models on
inference engines, delivered through messenger transports** (see the
[README](./README.md) for the positioning). The loop's shape is
decided UPFRONT by an explicit **Policy table**, driven by a
**Classifier** — not by the model itself. Every adapter (model,
transport, memory, etc.) is a Protocol implementation living in the
application that consumes Owela.

---

## The eight anti-trap principles

These rules are non-negotiable. They are the difference between a
framework and a pile of patches accreting on an application file —
which is exactly what Owela was extracted from. If you find yourself
breaking one of them, the design is wrong, not the rule.

### 1. No special cases in `executor.py`

Behaviour is policy-driven. If you want an `if` inside the executor
for some new case, you're describing a new `Policy` field, not a
special case. The executor's job is to walk through steps in order,
gated by `policy.enable_X` flags + the presence of runtime components.
That's it.

### 2. Tools are `@tool`-decorated functions, not dict schemas

The OpenAI function-call schema is autogenerated from the function
signature + the `params=` dict in the decorator. Schema and
implementation can never drift because they live next to each other.
If you write a tool, write the function and decorate it — never
hand-author a schema dict.

### 3. Steps are typed dataclasses

Every observable phase of a turn produces a typed Step subclass
(`RouterStep`, `PlanStep`, `ModelCallStep`, `ToolStep`,
`CritiqueStep`, `ReviseStep`, `ReplyStep`). Tracing, billing, and
eval recording walk the step list — they need types they can match
on, not freeform dicts.

Adding a new behaviour to the executor (e.g. a new "summarise"
phase) means adding a new Step subclass to `step.py` AND a new
executor branch gated by a Policy flag. Both, not one.

### 4. Hooks for cross-cutting concerns

Billing, tracing, persistence, PII redaction, eval recording — all
hooks. They subscribe to step events and observe. They never appear
inline in `executor.py`.

Hooks are concurrency-safe across users (the `Runtime` is a singleton
shared across requests). Don't keep mutable per-call state on a hook
instance unless you protect it.

Hooks NEVER raise. The HookRegistry catches and logs everything.

### 5. Transport is an adapter

All transport-specific code (WhatsApp HTTP calls, char caps, dead-URL
checks, typing-window awareness) lives in the Transport implementation
in the application package. The executor knows "send a text" and
"what's the typing window," not "POST to graph.facebook.com".

If you find yourself wanting to add WhatsApp-shaped logic to Owela:
stop. It belongs in the application's WhatsAppTransport impl.

### 6. One Runtime object holds everything

The `Runtime` is a frozen dataclass with all the registered adapters.
Built once at application startup. Tests substitute components via
constructor injection. There are no module-level singletons inside
Owela that hold per-request state.

### 7. No god-functions

`execute_turn` is the only orchestrator. The function body is
currently ~160 LOC (the surrounding file is ~210 LOC including
imports and the module docstring). If the body grows past 250 LOC,
that's the signal a new abstraction wants to come out — maybe a
Hook, maybe a new Step kind, maybe a new Policy field.

### 8. Owela is pure library

Zero application specifics live in `owela/`. The system prompt is
not here, the classifier prompt is not here, the WhatsApp credentials
are not here, the Gemma 4 image-dimensions-multiple-of-48 quirk is
not here. Every product-specific thing is registered into the Runtime
by the application layer.

If you're about to add a string of text that mentions Namibia,
WhatsApp, Gemma, or any specific product — you're working in the
wrong directory. Open `ongiini/` instead.

## The Step model

| Step type | Produced by | Key fields | v0 / v1? |
|---|---|---|---|
| `RouterStep` | Classifier (wrapped by executor) | `verdict`, `depth`, tokens | v0 |
| `PlanStep` | Planner | `plan_text` | v1 (slot exists) |
| `ModelCallStep` | Each model.complete() call | `turn`, `enable_thinking`, `reasoning_budget`, `finish_reason`, `tool_calls`, tokens | v0 |
| `ToolStep` | Each tool execution | `tool_name`, `tool_call_id`, `args_len`, `result_len`, `error` | v0 |
| `CritiqueStep` | Reviewer.critique() | `verdict` (`PASS`/`REVISE`), `reasons` | v1 (slot exists) |
| `ReviseStep` | Reviewer.revise() | `attrs["revised_reply"]` | v1 (slot exists) |
| `ReplyStep` | Transport.send | `reply_len`, `sent`, `dead_urls_stripped` | v0 |

All steps inherit from `Step` and carry the common fields
(`started_at`, `ended_at`, `tokens_in`, `tokens_out`, `cached_tokens`,
`attrs`).

To add a new step kind: declare the dataclass in `step.py`, add a
branch to `execute_turn`, gate it on a Policy flag.

## The Policy table

A `Policy` is a frozen dataclass. The fields that matter most for
extension work:

```python
@dataclass(frozen=True)
class Policy:
    name: str
    first_tool: ToolChoice              # AUTO | force_tool("name")
    max_steps: int = 6

    # v1 flags — keep False until the corresponding component is wired
    enable_planner: bool = False
    enable_critique: bool = False
    enable_interstitial: bool = False

    # Reasoning knobs (engine-specific; the Model adapter consumes them)
    reasoning_budget: int | None = 500
    enable_thinking_after_long_results: bool = True
    long_result_threshold_chars: int = 1000

    # Tool exposure — None = all, tuple = whitelist
    expose_tools: tuple[str, ...] | None = None
```

**Worked example: enable the planner only on SEARCH_DEEP turns.**

```python
# In application's policy table:
policy_table.set(
    VERDICT_SEARCH, DEPTH_DEEP,
    Policy(
        name="search_deep",
        first_tool=AUTO,
        max_steps=8,
        enable_planner=True,   # <-- flip this
    ),
)

# Plus register a Planner impl into the Runtime:
runtime = Runtime(
    ...,
    planner=YourPlannerImpl(),   # <-- new
)
```

No changes to `executor.py`. The phase fires gated on the flag AND
the component's presence — missing component + flag-on = phase
silently skipped.

## The Hook contract

Hooks are observe-only. They MUST be safe under concurrent invocation
across users (one HookRegistry, many concurrent requests). They MUST
NOT raise — the HookRegistry catches and logs, but defence in depth
matters.

Two events:

- `on_step(step, ctx)` — fired after each step is appended to the
  step list
- `on_turn_complete(steps, ctx)` — fired once at the end, after the
  ReplyStep lands

`ctx: TurnContext` carries `msg`, `policy`, `runtime`. Treat the
runtime as a service locator (read components out of it); never
mutate it.

Common hook patterns:
- Billing → subscribe to `on_turn_complete`, walk the step list,
  emit one usage log line per ModelCallStep aggregate.
- Tracing → subscribe to `on_turn_complete`, dump structural
  signals (no content) to a JSONL file.
- Persistence → subscribe to `on_turn_complete`, call
  `runtime.memory.record_turn` (or skip if a particular ToolStep
  fired — see Ongiini's `OngiiniMemoryRecordingHook`).

## The Protocol set

Every adapter implements one or more of these Protocols. Each is
small (3-5 methods) and documented in its source file. What the
executor asks of each:

- **`Model`** — `complete(req: ModelRequest) -> ModelResponse`. ONE
  round-trip. No internal retries. Surface engine knobs (cached_tokens,
  reasoning) on the response.
- **`Transport`** — `acknowledge(msg)`, `send_interstitial(...)`,
  `send(user_id, body, policy, *, used_search=False)`. Owns reply
  hygiene + transport metadata (`typing_window_s`, `max_message_chars`,
  `format`).
- **`MemoryProvider`** — `assemble_messages(msg, policy, steps) ->
  list[dict]` is the ONE function that decides what the model sees.
  Plus `record_turn`, `delete_all`, `list_all`, `format_facts`.
- **`Classifier`** — `classify(msg) -> ClassifierResult`. Fail-safe:
  any error returns `ClassifierResult(verdict="NONE", depth="SHALLOW")`.
- **`Planner`** (v1) — `plan(msg, policy, prior_steps) -> PlanStep`.
- **`Reviewer`** (v1) — `critique(msg, draft, prior_steps, policy)`
  and `revise(msg, draft, critique, prior_steps, policy)`.
- **`Hook`** — `on_step` and/or `on_turn_complete`. See above.

## Extending Owela — the four common cases

### Add a tool

```python
from owela import ToolContext, tool

@tool(
    name="weather",
    description="Get current weather for a city.",
    params={"city": "City name."},
)
async def weather(city: str) -> str:
    return await your_weather_api(city)

# Tools that need runtime access take ctx: ToolContext as their first
# arg — the decorator excludes ctx from the schema:
@tool(name="delete_my_data")
async def delete_my_data(ctx: ToolContext) -> str:
    """Wipe the user's data."""
    await ctx.runtime.memory.delete_all(ctx.user_id)
    return "Done."
```

Register the tool in the application's `ToolRegistry`. If you want
it forced on turn 1 for a specific verdict, add a `PolicyTable` entry
using `force_tool("weather")` as `first_tool`.

### Add a new transport

Implement the `Transport` protocol in the application package. Three
methods (`acknowledge`, `send_interstitial`, `send`), four class
attributes (`name`, `typing_window_s`, `max_message_chars`, `format`).
Register the instance into the `Runtime` at app startup.

Reply hygiene (dead-URL stripping, char capping, format normalisation)
lives inside the transport's `send` method — it's medium-specific
and shouldn't be in the executor.

### Add a new model engine

Implement the `Model` protocol. The job is to:
1. Convert `ModelRequest` into your engine's call shape.
2. Surface engine-specific knobs via the request's `policy` field
   (read `reasoning_budget`, `enable_thinking`).
3. Convert the response back to `ModelResponse`, including the
   prefix-cache-aware `tokens_in`, `tokens_out`, `cached_tokens`
   tuple — these are what make billing honest.

See `ongiini/models/vllm_gemma.py` for the canonical vLLM example.

### Add a new step / phase

Three steps:

1. Declare the typed Step subclass in `step.py`.
2. Add a branch in `execute_turn` gated by a Policy flag AND the
   relevant runtime component being non-None.
3. (Optional) Add the corresponding protocol to `runtime.py` if the
   phase needs a pluggable component.

Tests: add one in `tests/test_executor.py` using the `ScriptedModel`
fixture pattern; assert the new step appears in the result and the
hook layer sees it.

### Register a skill

Skills are named reference blocks the application registers with the
Runtime. The framework provides `Skill` and `SkillRegistry`; rendering
into the system prompt and the on-demand load tool live in the
application layer.

```python
from owela import Skill, SkillRegistry

registry = SkillRegistry([
    Skill(
        name="oshiwambo",
        description="...what + when...",
        content="...full markdown...",
        load="always",  # or "on_demand" (default)
    ),
])
runtime = Runtime(..., skills=registry)
```

The application's `MemoryProvider` calls `runtime.skills.manifest()` to
get a system message containing the catalogue (and inlined content of
every `load="always"` skill). On-demand skills appear as manifest
entries only; the application supplies a `load_skill(name)` tool that
reads `ctx.runtime.skills.get(name)` and returns the content. See
`ongiini/tools/skill_tools.py` and `ongiini/skills_loader.py` for the
canonical filesystem-loader pattern.

The frontmatter format matches Claude's skill standard (just `name` +
`description`); the `load` field is an Owela extension that Claude
ignores. A skill file works in both ecosystems without changes.

## What NOT to put in Owela

If you find yourself reaching for any of these inside `owela/`, stop:

- A system prompt (it's application-specific)
- A product knowledge document (application)
- Transport credentials (application — typically environment-injected
  into the Transport adapter)
- Classifier prompt content (application — the Classifier protocol
  doesn't care what your prompt says)
- PII redaction rules (application — typically in a hook or in the
  storage path)
- Model-specific quirks (application — e.g. Gemma 4's image-dim
  multiples of 48 lives in `ongiini/api/main.py::_resize_for_gemma4`,
  not in `owela/`)
- Anything that mentions Namibia, WhatsApp, Gemma, vLLM, or any
  specific product / brand

## Testing

Unit tests live in `owela/tests/`. The patterns to follow:

- **`ScriptedModel`** (in `test_executor.py`) — a Model fake that
  returns a pre-recorded sequence of responses. Use this for any
  test that walks the executor end-to-end.
- **Protocol fakes over `MagicMock`** — write small classes that
  implement the protocols (see `FakeTransport`, `FakeClassifier`,
  `FakeMemory` in `test_executor.py`). MagicMock works but obscures
  contract violations; explicit fakes catch them.
- **Run with**: `pytest owela/tests` from the repo root, or
  `pytest owela/tests/test_executor.py -v` for a single file.
- **Concurrency assertions**: use real `asyncio.sleep` and measure
  wall time to verify parallel dispatch — see
  `test_parallel_dispatch_is_concurrent`.

## Known limitations / open questions

These are documented "we know this isn't great yet" items. Don't
rediscover them.

- **Summarisation isn't a protocol yet.** Rolling-summary of long
  histories is application-side concern (see `ongiini/summary.py`)
  rather than an Owela `Summarizer` protocol. Promoting it is a
  candidate for v1.
- **Single-tenant Runtime.** One Runtime per process, no first-class
  multi-tenant story. Fine for single-app deployments; would need
  thought for hosting multiple Owela apps on one process.
- **No streaming response support.** The Model adapter returns a
  complete `ModelResponse`; there's no incremental-yield API.
  Reasonable for messenger transports where replies are atomic;
  would matter for a hypothetical web-UI transport.
- **No durable execution / checkpointing.** A crashed turn loses
  state. Acceptable when the underlying transport (WhatsApp) retries
  the inbound webhook on our 500. Would need work for shapes where
  partial work is expensive (long research turns).
